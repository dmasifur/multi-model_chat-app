# Phase 3 — Auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire up Auth.js (NextAuth v5) with the Drizzle adapter against Phase 2's `user`/`account`/`session`/`verificationToken` tables, add GitHub + Google OAuth, a sign-in page, and route-protecting middleware — so every later phase can read `session.user.id` and gate access to the chat UI.

**Architecture:** A single `auth.ts` at the project root configures `NextAuth()` with `DrizzleAdapter` (pointed at Phase 2's tables) and the GitHub/Google providers, using JWT session strategy (the standard Auth.js pattern for OAuth-only sign-in — the adapter still persists `user`/`account` rows, but sessions themselves are signed JWTs, avoiding a DB round-trip per request). A thin `app/api/auth/[...nextauth]/route.ts` exposes the handlers. Next.js 16 renames `middleware.ts` to `proxy.ts`; `proxy.ts` wraps `auth()` to redirect unauthenticated requests to `/sign-in`, delegating the actual routing decision to a small pure, unit-tested helper (`lib/auth/is-public-path.ts`) so the redirect logic doesn't require mocking Next's request internals to test.

**Tech Stack:** `next-auth@beta` (Auth.js v5), `@auth/drizzle-adapter`, Bun, Vitest. No new database tables — Phase 2 already created everything the adapter needs.

**Spec:** `docs/superpowers/specs/2026-08-25-multi-model-chat-design.md`

- Tests run with **Vitest** via `bun run test`.
- Branch: all Phase 3 work on **`phase-3-auth`**, off `phase-2-db` (which is reviewed/ready but not yet merged to `main` — same situation as Phase 2 off Phase 1; see note below); merged via PR.
- Commits: **small, meaningful chunks**; **no `Co-Authored-By: Claude` trailer**.
- Secrets never committed: `.env` is gitignored; only `.env.example` is tracked (already has the `AUTH_*` placeholders from Phase 1 — no changes needed to it).
- Auth (from spec, verbatim): **Auth.js (NextAuth v5) + Drizzle adapter, GitHub + Google OAuth.** Middleware protects chat routes; unauthenticated users hit a sign-in page. (Chosen over Clerk to keep user identity in our own Postgres for clean `userId` foreign keys.)
- Auth.js's env var convention: a provider added as `providers: [GitHub, Google]` (no inline `clientId`/`clientSecret`) auto-reads `AUTH_GITHUB_ID`/`AUTH_GITHUB_SECRET` and `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` — these names already match `.env.example` exactly.

**Note on branch base:** Phase 2 (`phase-2-db`) is reviewed and ready but not yet merged to `main` (kept local, no remote yet, per user instruction). Task 1 branches `phase-3-auth` off `phase-2-db`, since that is where the live schema and migration actually are. When Phase 1/2 are eventually merged, `phase-3-auth` rebases onto `main` in the ordinary way.

**Note on OAuth credentials:** `AUTH_GITHUB_ID`/`AUTH_GITHUB_SECRET`/`AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` are blank in `.env.example` and will be blank in the developer's local `.env` until they create real OAuth apps on GitHub's and Google Cloud's developer dashboards — that is an external account action only a human can do (this plan cannot and does not attempt it). Every automated step in this plan (imports, unit tests, `bun run build`) works correctly with blank provider credentials, because Auth.js does not validate them until an actual OAuth redirect happens. Live sign-in is a manual, post-plan verification step once the developer supplies real credentials — noted at the end, not a blocking task.

## File Structure

- `auth.ts` — **create.** Root NextAuth config: `DrizzleAdapter`, GitHub + Google providers, JWT session strategy, callbacks exposing `session.user.id`. Exports `{ handlers, auth, signIn, signOut }`.
- `types/next-auth.d.ts` — **create.** Module augmentation adding `id: string` to `Session['user']` so `session.user.id` is typed everywhere it's read later.
- `lib/__tests__/auth.test.ts` — **create.** Unit test asserting `auth.ts`'s exports have the right shape (no network calls).
- `app/api/auth/[...nextauth]/route.ts` — **create.** Re-exports `GET`/`POST` from `auth.ts`'s handlers.
- `app/api/auth/[...nextauth]/__tests__/route.test.ts` — **create.** Unit test asserting the route re-exports functions.
- `lib/auth/is-public-path.ts` — **create.** Pure function: given a pathname, is it reachable without a session?
- `lib/auth/__tests__/is-public-path.test.ts` — **create.** Unit test covering public and protected paths.
- `proxy.ts` — **create.** Next.js 16's middleware convention (renamed from `middleware.ts`). Wraps `auth()`, uses `isPublicPath` to decide whether to redirect to `/sign-in`.
- `app/sign-in/page.tsx` — **create.** Server component with two `<form>`s using inline server actions (`signIn('github', …)` / `signIn('google', …)`) — no client JS bundle needed.

- [ ] **Step 4: Write `auth.ts`**

```ts
import NextAuth from 'next-auth';
import GitHub from 'next-auth/providers/github';
import Google from 'next-auth/providers/google';
import { DrizzleAdapter } from '@auth/drizzle-adapter';
import { db } from '@/lib/db';
import { users, accounts, sessions, verificationTokens } from '@/lib/db/schema';

export const { handlers, auth, signIn, signOut } = NextAuth({
  adapter: DrizzleAdapter(db, {
    usersTable: users,
    accountsTable: accounts,
    sessionsTable: sessions,
    verificationTokensTable: verificationTokens,
  }),
  providers: [GitHub, Google],
  session: { strategy: 'jwt' },
  callbacks: {
    jwt({ token, user }) {
      if (user) {
        token.id = user.id;
      }
      return token;
    },
    session({ session, token }) {
      if (session.user) {
        session.user.id = token.id as string;
      }
      return session;
    },
  },
});
```

- [ ] **Step 3: Write `lib/auth/is-public-path.ts`**

```ts
const PUBLIC_PATHS = ['/sign-in'];

export function isPublicPath(pathname: string): boolean {
  if (pathname.startsWith('/api/auth')) {
    return true;
  }
  return PUBLIC_PATHS.includes(pathname);
}
```

- [ ] **Step 5: Write `proxy.ts`**

```ts
import { NextResponse } from 'next/server';
import { auth } from '@/auth';
import { isPublicPath } from '@/lib/auth/is-public-path';

export const proxy = auth((req) => {
  if (!req.auth && !isPublicPath(req.nextUrl.pathname)) {
    return NextResponse.redirect(new URL('/sign-in', req.nextUrl.origin));
  }
});

export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico).*)'],
};
```

## Manual verification (post-plan, once real OAuth credentials exist)

This is not a plan task — it requires the developer to create OAuth apps on GitHub's and Google Cloud's developer dashboards (an external account action) and paste real client IDs/secrets into local `.env`. Once done:

1. `bun run dev`, visit `/` while signed out → redirected to `/sign-in`.
2. Click "Sign in with GitHub" → completes OAuth → redirected back to `/` → `user`/`account` rows appear in Postgres.
3. Repeat for Google.
4. Visit `/sign-in` directly while already signed in — should not redirect-loop (not enforced by this phase's logic, since `isPublicPath('/sign-in')` is always `true` regardless of session state; note this only if it becomes a UX problem later, not a defect now).
